# ข้อเสนอ: กรอบตรวจสอบว่าวิธีคำนวณมูลค่า "ผิด" หรือไม่ (ไม่ใช่แค่ลองแล้วดูผล)

*เขียนโดย Hermes (Bubu) ตามคำขอ CIO 2026-10-08 — ส่งให้ Opus/โมเดลที่แข็งกว่าตรวจสอบและพัฒนาต่อ*
*บริบท: เกิดจากคำถาม CIO ว่า "จะรู้ได้ยังไงว่า business-type valuation map (VS2 addendum 1D) แต่ละประเภทคำนวณถูกจริง ไม่ใช่แค่ลองแล้วดูผล"*

## ปัญหาที่ต้องแก้

AMZN v3.2→v3.4 แสดงให้เห็นว่าโมเดลเดิมผิดมา 5 รอบติดโดยไม่มีใครในทีมรู้ตัว เพราะ:
1. ไม่มี external cross-check อัตโนมัติ (รู้ตัวเพราะ CIO สังเกตเองว่า "ไม่มีที่ไหนให้ต่ำกว่า $200")
2. ไม่มีกลไกตรวจว่า "วิธีที่เลือกเหมาะกับธรรมชาติธุรกิจนี้จริงไหม" ก่อนเริ่มคำนวณ
3. judgment call ที่กำกวม (WACC source selection, peer selection) ถูกเลือกหลังรู้ทิศทางผลลัพธ์ที่อยากเห็น โดยไม่มีใครรู้ตัวว่ากำลังทำ

**คำถามที่ CIO ถาม:** ระบบ business-type map ที่เพิ่งเขียนเข้า CLAUDE.md (10 ประเภท) จะรู้ได้ยังไงว่าแต่ละประเภทคำนวณถูกจริง ไม่ใช่แค่สมมติเอาเอง

## คำตอบ: ไม่มีทาง "รู้ถูกแน่นอนล่วงหน้า" — แต่มี 4 ชั้นตรวจสอบที่ลดความเสี่ยงได้มาก

---

## ชั้น A — Pre-Analysis: ตรวจก่อนเริ่มคำนวณ (ป้องกันไม่ให้เลือกวิธีผิดตั้งแต่ต้น)

### A1. Theoretical Fit Test (บังคับ ก่อน Atlas ส่งข้อมูลให้ Emma)
สำหรับทุกประเภทใน business-type map ต้องตอบคำถามนี้เป็นลายลักษณ์อักษรก่อนเริ่ม:
- "ทำไมวิธีนี้ถึงเหมาะกับธรรมชาติธุรกิจนี้ (ไม่ใช่แค่ 'เป็นธรรมเนียมที่ใช้กัน')"
- ตัวอย่างคำตอบที่ผ่าน: "ธนาคารใช้ P/B เพราะ book value = regulatory capital ภายใต้ Basel ไม่ใช่แค่ asset ทางบัญชี"
- ตัวอย่างคำตอบที่ไม่ผ่าน: "ใช้ DCF เพราะทุกหุ้นใช้กัน"

### A2. Classification Audit Trail (บังคับ)
Atlas ต้องบันทึก **เกณฑ์เชิงตัวเลข** ที่ใช้จัดประเภท ไม่ใช่ความเห็น:
- "ลงทุนหนัก" = PV(TV)/EV > 70% (**คำนวณอัตโนมัติจากตัวเลขจริง ไม่ใช่เลือกเอง** — จุดนี้ออกแบบมาดีแล้วใน VS2)
- หุ้นประเภทอื่นที่ยังไม่มีเกณฑ์ตัวเลขชัด (เช่น "SaaS โตเร็ว", "Cyclical") — **ต้องเติมเกณฑ์ตัวเลขให้ครบก่อนใช้งานจริง** (ดู Open Item ท้ายเอกสาร)

### A3. Multi-Method Mandatory Cross-Check (ไม่ใช่แค่ optional)
ทุกประเภท (ไม่ใช่แค่ชั้น 2 ของหุ้นลงทุนหนัก) ต้องมี**วิธีสำรองอย่างน้อย 1 วิธี** คำนวณคู่กันเสมอ แล้ว**รายงานทั้งคู่** แม้จะใช้วิธีหลักเป็น final:
- ถ้าห่างกัน ≥25% → บังคับ reconciliation table (ตามกฎ Multi-Segment ที่มีอยู่แล้ว) **ก่อน**สรุปผล ไม่ใช่หลัง

---

## ชั้น B — At-Analysis: ตรวจระหว่างคำนวณ (จับ motivated reasoning แบบที่เพิ่งคุยกัน)

### B1. Anchor-Proximity Flag (ใหม่ — เสนอเพิ่ม)
ถ้า **ใครก็ตาม** (CIO, Charlie, Opus) เคยพูดตัวเลขเป้าหมายในแชท/บทสนทนา **ก่อน**เริ่มคำนวณจริง →
- บันทึกตัวเลขนั้นไว้แยก (ไม่ใส่ในไฟล์งาน ตามที่ Opus ทำกับ VS2 brief อยู่แล้ว — ดีมาก)
- **หลัง**ได้ผลจริง ถ้าผลลัพธ์อยู่ในช่วง ±5% ของตัวเลขที่เคยพูดไว้ก่อน → auto-flag "ANCHOR_PROXIMITY_WARNING" ให้ Morgan ตรวจเพิ่มเติมเจาะจุด judgment-call ทุกจุดอีกรอบ (ไม่ได้แปลว่าผิด แต่ต้องพิสูจน์แรงกว่าปกติ)
- เคส AMZN v3.4: ผล $201.47 ใกล้กับที่ CIO เคยพูดว่า "ไม่มีที่ไหนต่ำกว่า $200" มาก → **เข้าเกณฑ์นี้พอดี ควรถูก flag ไว้แล้วจริงๆ**

### B2. Degrees-of-Freedom Audit (ใหม่ — เสนอเพิ่ม)
ให้ Morgan นับและบันทึก **ทุกจุดที่เป็น judgment call (เลือกได้มากกว่า 1 ทาง)** ในการวิเคราะห์ ไม่ใช่แค่จุดที่เป็น error:
- ตัวอย่างจาก AMZN v3.4: (1) WACC stale-rate threshold (เลือก 75bps ทำไมไม่ 50 หรือ 100) (2) เลือกทิ้ง 4/6 แหล่ง WACC ภายนอก (3) เลือก peer META/GOOGL สำหรับ Ads ไม่ใช่ peer อื่น
- สำหรับแต่ละจุด: **ทำ sensitivity table** — ถ้าเลือกทางตรงข้าม FV เปลี่ยนไปเท่าไหร่?
- ถ้ามี judgment call ที่เดี่ยวๆ เปลี่ยนผลลัพธ์เกิน 15-20% ของ FV ทั้งหมด → ต้องมีเหตุผลเชิงทฤษฎีรองรับแน่นหนากว่าปกติ (อ้าง source มากกว่า 1, ไม่ใช่แค่เลือกเพราะ "ดูสมเหตุผลกว่า")

### B3. Blind Re-derivation Test (ใหม่ — เสนอเพิ่ม, ใช้เฉพาะเคสที่ anchor-proximity trigger)
เมื่อ B1 trigger ให้ dispatch **subagent คนที่สองที่ไม่เห็นบทสนทนาเดิม ไม่รู้ตัวเลขที่คาดหวัง** ให้คำนวณ FV ใหม่จาก data package เดียวกัน (Atlas's data) แต่ไม่เห็น brief ที่มีผลลัพธ์เดิมปนอยู่
- ถ้าได้ผลใกล้เคียงกัน (±10%) โดยไม่รู้เป้าหมาย → เพิ่มความเชื่อมั่นว่าไม่ใช่ motivated reasoning
- ถ้าห่างกันมาก → แปลว่ามี judgment call ที่ sensitive ต่อผู้คำนวณ ต้องหา root cause ว่าต่างกันที่ไหน

### B4. Symmetric-Direction Requirement (มีอยู่แล้วใน VS2 — ยืนยันต่อ)
ทุกแก้ไขต้องรายงาน **ทั้งขั้นที่ดันขึ้นและลง** พร้อมตัวเลข attribution แยกขั้น (ตามที่ AMZN v3.4 ทำแล้ว — เป็น best practice ที่ดี ให้คงไว้)

## ชั้น C — Internal Consistency (ตรวจว่าโมเดลขัดกันเองไหม)

### C1. Equity₅ Reconciliation (มีอยู่แล้วใน VS2 1.4 — ยืนยันต่อ)
Equity₅ ที่คำนวณจากโมเดล ต้อง ≈ Equity₀×(1+cost of equity)⁵ ห่างเกิน 10% ต้องอธิบาย

### C2. Cross-Segment Consistency (มีอยู่แล้วจาก AMZN segment rule — ขยายให้เป็นกฎทั่วไป)
ถ้ามีการแยกส่วนธุรกิจ (segment DCF) ผลรวมต้อง reconcile กับโมเดลรวมบริษัทเสมอ — ใช้กับทุกหุ้นที่มี multi-segment ไม่ใช่แค่ AMZN

### C3. No-Growth Floor Check (เสนอขยายเป็นกฎทั่วไป)
FV ที่ได้ต้องไม่ต่ำกว่า **no-growth value** (NOPAT ปัจจุบัน ÷ WACC) เว้นแต่มีเหตุผลชัดเจน (เช่น terminal RONIC < WACC จริงและระบุไว้) — เจอปัญหานี้กับ Bear's AMZN v3.1 มาแล้ว ควรเป็นกฎถาวร

## ชั้น D — Post-Analysis: Backtest ระยะยาว (การพิสูจน์จริงเพียงอย่างเดียวที่มี)

### D1. Analyst Scorecard (มีอยู่แล้วใน Vera Protocol — ต้องทำให้เข้มขึ้น)
- เสนอเพิ่ม: แยก scorecard **ตาม business-type** ไม่ใช่รวมทุกหุ้นเป็นก้อนเดียว — เพื่อรู้ว่า "DCF+multiples สำหรับหุ้นลงทุนหนัก" แม่นกว่าหรือแย่กว่า "DCF ล้วนสำหรับธุรกิจทั่วไป" จริงหรือไม่ เมื่อเทียบ realized price หลัง 6/12 เดือน

### D2. Method-Level Calibration Table (ใหม่ — เสนอเพิ่ม)
ตารางที่ Vera สร้างทุกไตรมาส:

| Business Type | # Analyses | Avg FV error vs realized (6mo) | Avg FV error vs realized (12mo) |
|---|---|---|---|
| DCF ล้วน | | | |
| DCF+multiples (TV>70%) | | | |
| SaaS (Rule of 40) | | | |
| ... | | | |

ถ้าประเภทไหน error สูงกว่าค่าเฉลี่ยต่อเนื่อง 4 ไตรมาส → ต้อง review วิธีของประเภทนั้นโดยเฉพาะ (ไม่ต้อง wait 8Q เหมือน Return-side rule เพราะนี่คือ methodology ไม่ใช่ gate)

### D3. TRIAL Period กับทุก Layer ใหม่ (ตามที่ Opus ทำกับ VS2 ชั้น 2 แล้ว — ขยายเป็นมาตรฐาน)
ทุกกฎ/วิธีใหม่ที่เพิ่มเข้ามา (ไม่ใช่แค่ชั้น 2) ควรมี**วันที่รีวิวชัดเจน** ก่อนล็อกเป็นมาตรฐานถาวร — ป้องกันการยึดติดกับวิธีที่ดูดีตอนคิด แต่ไม่เคยพิสูจน์จริง

## สรุปสั้น: ลำดับการตรวจที่เสนอ

```
ก่อนคำนวณ:   A1 (ทำไมวิธีนี้เหมาะ) → A2 (เกณฑ์ตัวเลขจัดประเภท) → A3 (บังคับมี 2 วิธีเสมอ)
ระหว่างคำนวณ: B1 (เคยพูดเลขเป้าไว้ไหม) → B2 (judgment call ไหนกระทบมาก) → B3 (ถ้า flag ให้ blind re-derive) → B4 (ต้องมีทั้ง 2 ทิศ)
หลังคำนวณ:    C1-C3 (ขัดกันเองไหม)
ระยะยาว:      D1-D3 (ราคาจริงพิสูจน์ย้อนหลัง)
```

## Open Items ที่ยังไม่มีคำตอบ (ขอ Opus/โมเดลที่แข็งกว่าช่วยตัดสิน)

1. **เกณฑ์ตัวเลขของ classification ที่เหลือ** — ตอนนี้มีแค่ "ลงทุนหนัก" ที่ auto-trigger ด้วย PV(TV)/EV>70% ประเภทอื่น (SaaS, Cyclical, Biotech ฯลฯ) ยังใช้ "ดูแล้วจัด" อยู่ — ควรมีเกณฑ์ตัวเลขแบบเดียวกันไหม และควรเป็นอะไร
2. **Anchor-proximity threshold ที่เหมาะสม** — ผมเสนอ ±5% จากตัวเลขที่เคยพูดไว้ก่อน แต่ไม่มีหลักฐานว่าเลขนี้เหมาะสม ควรปรับไหม
3. **ต้นทุน vs ประโยชน์ของ Blind Re-derivation (B3)** — ใช้ subagent สองรอบทุกครั้งที่ anchor-proximity trigger จะเพิ่ม cost/เวลามาก ควรจำกัดแค่หุ้นที่จะ deploy จริงเท่านั้นไหม หรือทำกับทุกเคส
4. **D2 Method-Level Calibration ต้องรอข้อมูลสะสมนานแค่ไหนถึงมีความหมายทางสถิติ** — ตอนนี้มีหุ้นวิเคราะห์เต็มไม่มาก การแยกตาม business-type อาจทำให้แต่ละกลุ่มมี sample size เล็กเกินจะสรุปอะไรได้จริงในปีแรก
